1.Goal, scope, and what is deliberately excluded

For a remote-enabled OFFLINE table, a Pinot server holds no segment data at all. Every query reads exactly the byte ranges it needs (the relevant columns' index structures) directly from the deep store, computes over them in per-query memory buffers, returns results to the broker, and frees everything. The deep store is not a backup here — it is the storage engine.

  • In scope: OFFLINE tables, segment format v3, S3-compatible deep stores via PinotFS (S3 / MinIO / GCS), server-side only — brokers, controllers, and Helix segment assignment are unchanged.
  • Deliberately excluded from v1: any disk cache, any block cache, LRU/eviction machinery, lazy segment materialization, tier relocation. Always query S3. The seams are kept so a cache can be added later without redesign, but v1 ships without one.
  • Invariants (non-negotiable):
    1. Tables without the config run the byte-identical classic local path — zero regression.
    2. Opt-in twice: instance kill switch (default off) + per-table config.
    3. Any degraded result is flagged in the broker response — never silent.
Two unavoidable residencies (physics, not caching): (1) Segment metadata lives in server memory — to turn “this query needs the dictionary of column bla” into “bytes 1,204,224–1,834,511 of s3://…/columns.psf”, the server needs each segment's index_map and metadata.properties (a few KB per segment), fetched once at the OFFLINE→ONLINE transition. Without it, every query would spend two extra S3 round-trips learning where its bytes are. (2) A per-query fetch-bytes cap is mandatory — with no disk involved, an unfiltered scan would pull gigabytes into per-query RAM and OOM-kill the server. remote.query.max.fetch.bytes fails such a query fast with an actionable error. Memory safety, not a cache.

2.What happens when you query — end to end

SELECT COUNT(*) FROM bla WHERE bla = 1 against a remote-enabled table:

  1. Broker — nothing new. The routing table (built from Helix assignment, unchanged) scatters the query to the servers hosting bla's segments.
  2. Server: segment resolution — each target segment was registered at its OFFLINE→ONLINE transition: the server fetched the metadata trio (metadata.properties, index_map, creation.meta) from the segment's segment.download.url in ZK — the S3 location, which already exists in Pinot for every segment — parsed it into the in-memory registry, and reported ONLINE. No data bytes were downloaded.
  3. Fetch planning — RemoteAwareFetchPlanner inspects the query: predicate on bla → needs bla's dictionary + inverted index (or forward index if no inverted exists); COUNT(*) needs no projection columns. The in-memory index_map converts that to exact byte ranges within columns.psf.
  4. Admission check — total planned bytes vs remote.query.max.fetch.bytes; over → fail fast with “query requires X MB of remote reads; cap is Y MB”.
  5. Fetch — ranges are sorted, coalesced (gaps < threshold merged into one GET), and fetched in parallel via ranged S3 GETs into the query's QueryScopedFetchBuffer (memory, accounted, deadline-bounded).
  6. Execute — the standard operator tree runs unmodified: index readers see ordinary PinotDataBuffers that happen to be backed by the fetched ranges. Per-segment results are computed exactly as on local data.
  7. Return & free — server combines, broker merges, client gets the count. The query's buffers are freed on release(). Nothing was written to disk; nothing survives the query.

5.Build steps

Dependency-ordered; each step has a proof gate. After Step 5 the system answers queries from S3 end to end; Steps 6–9 make it fast, safe, and shippable.

Step 0Dev harness — the correctness oracle

  • Docker compose: MinIO + controller + broker + 2 servers (quickstart configs).
  • Segment generator producing one real v3 segment carrying every index type to support (dictionary, forward, inverted, range, bloom, null-vector) from a few million synthetic rows.
  • Golden-query set — aggregations, filters per index type, SELECT *, group-by — expected results captured against local execution.
Proof gate: golden queries pass on a plain local cluster. Every later step is measured against this oracle.

Step 1Ranged reads in PinotFS

  • pinot-spi: default int readRange(URI uri, long offset, byte[] buf, int bufOffset, int length) (default throws — third-party FS implementations keep compiling).
  • Implement in S3PinotFS (GetObject with Range header) and LocalPinotFS (seek+read, for tests).
Proof gate: unit test reads known ranges through both implementations, including EOF-truncated tails.

Step 2RemoteSegmentRegistry — metadata in memory, once

  • At OFFLINE→ONLINE for a remote table: resolve segment.download.url from ZK, fetch only the metadata trio (tar header-range read or an untarred layout — decided by the Step 0 spike), parse index_map into (column, indexType) → (offset, size), keep in a ConcurrentHashMap<segmentName, RemoteSegmentEntry>. Entry also records CRC and total size.
  • Refresh messages re-fetch metadata (CRC change → new entry). OFFLINE/DROP transitions remove the entry. Failure to fetch metadata at transition → Helix ERROR, exactly like a failed download today.
Proof gate: ONLINE registers with correct index_map offsets (validated against the real segment); refresh swaps CRC; DROP clears; a server restart re-registers from ZK without touching data bytes.

Step 3QueryScopedFetchBuffer + RangeFetcher

  • QueryScopedFetchBuffer: per-(query, segment) container mapping fetched ranges → memory (direct ByteBuffers). Byte-accounted against remote.query.max.fetch.bytes (admission errors before fetching). Freed wholesale on release() — try/finally, leak-checked in tests.
  • RangeFetcher: sorts requested ranges, coalesces gaps < coalesce.gap.bytes into single GETs, executes on a bounded pool via PinotFS.readRange, retries with backoff, deduplicates identical in-flight ranges within the query, emits metrics (GETs, bytes, latency).
Proof gate: coalescing (5 adjacent ranges → 1 GET); cap enforcement (over-budget plan → admission error, zero GETs fired); buffers freed on close (allocation tracker); concurrent fetches within one query dedupe.

Step 4RemotePinotDataBuffer

  • Extends PinotDataBuffer; a view (segment, baseOffset, size) over columns.psf; every accessor (getByte/getInt/getLong/getDouble/getBytes/copyTo) resolves against the query's QueryScopedFetchBuffer.
  • Reads inside prefetched ranges are pure memory. A read outside them (planner under-fetch) triggers a synchronous ranged GET — correct but counted (REMOTE_SYNC_MISSES; the planner is iterated until ≈0).
  • view(start, end) supported (index readers rely on views); all write methods throw.
Proof gate: property test — deterministic pseudo-random file; every accessor compared against PinotByteBuffer over thousands of random (offset, length) pairs; sync-miss path fetches and serves correctly.

Step 5RemoteSegmentDirectory + loader — first end-to-end milestone

  • RemoteSegmentDirectoryLoader (registered as remote): opens a segment purely from the registry entry — no local files at all.
  • Reader.getIndexFor(col, type) → RemotePinotDataBuffer view from the index-map entry.
  • prefetch(FetchContext) → ranges → RangeFetcher (async); acquire → deadline-bounded wait for planned ranges; release → free the query's buffers.
Proof gate: golden-query harness — the same segment queried once locally, once remotely from MinIO: identical results on every query. “Pinot answered from S3, nothing on disk.”

Step 6RemoteAwareFetchPlanner

  • planFetchForPruning: bloom/range structures for predicate columns (small ranges; enables segment pruning without fetching data columns). ZK time-range pruning happens before any fetch, as today.
  • planFetchForProcessing: per query column — dictionary + forward index, plus inverted/range/sorted/json index when segment metadata says it exists and the predicate can use it.
  • No-op for local segments (planner checks the directory type) — zero overhead on the classic path.
Proof gate: exact planned (column, indexType) sets asserted per representative query; golden filter query completes with zero synchronous misses after prefetch.

Step 7Semantics: deadlines, failures, partial results

  • acquire waits min(remaining query deadline, remote.fetch.timeout); expiry → the segment is reported missing for this query — Pinot's existing flagged partial-result semantics.
  • S3 failure after retries → same flagged path; circuit breaker on consecutive failures per endpoint.
  • Strict mode: query option failOnPartialRemote — error instead of any partial result (audits).
  • Admission fail-fast (Step 3) is a query error, not a partial: “requires X MB remote reads, cap Y MB”.
Proof gate: deadline expiry → flagged partial, no parked threads; MinIO killed mid-query → flagged partial + breaker opens; strict option → error; oversized scan → fail-fast message.

Step 8Table config + wiring

  • Table config: "remoteQueryConfig": { "enabled": true } — validation: OFFLINE tables only.
  • Instance kill switch pinot.server.instance.remote.query.enabled=false (default off).
  • Regression test: a table without the config runs the byte-identical classic path (assert the default loader and default planner are used).

Step 9Validation battery + benchmark report

  • Full battery below (§9) + the numbers table: latency per query shape, GETs/query, bytes/query, $/query, classic-path A/B vs master proving zero local regression.

# server.conf (instance level)

pinot.server.instance.remote.fetch.parallelism=8
pinot.server.instance.remote.fetch.timeout.seconds=30

# table config (OFFLINE only)

  "enabled": true
}

SET failOnPartialRemote = true;

7.Hard problems and how the design answers them

ProblemAnswer in this design
Big query OOM-kills the server — with no disk, unbounded fetches land in RAM Per-query byte cap checked at admission, before any GET — exact sizes are known from the in-memory index_map. Over the cap → fast, actionable error. The disk-full concern from the lazy-loading discussion, answered at the memory level.
Warm-path regression — buffer reads are Pinot's hottest path Remote buffers are a separate class chosen at segment-open time; local segments keep existing mmap buffers untouched. CI benchmark gate.
Every query pays S3 latency — including the same query twice Accepted, by explicit scope: “always query S3” is the v1 contract. Latency floor ≈ one coalesced GET round-trip (tens of ms) + transfer. The SegmentDirectory seam admits a cache later without redesign (§10).
Planner under-fetch — each miss is a synchronous ~30 ms read on a query thread Planner over-fetches rather than under-fetches; REMOTE_SYNC_MISSES alarms; iterate until ≈0 on the golden set.
S3 request economics — many small GETs cost real money Range coalescing + bounded parallelism + per-table rate limit; benchmark report includes $/query so the trade is explicit and tunable.
Consistency on segment refresh Registry entries carry the CRC; refresh swaps the entry; in-flight queries finish on the old entry's ranges, new queries see the new one.
Selection-heavy queries (SELECT *, unfiltered scans) They plan huge fetch sets and hit the admission cap with a clear error — the feature targets filtered/aggregate analytics over cold data, and says so loudly rather than degrading silently.

9.Validation battery

  1. Correctness: golden queries, local vs remote parity on every index type; refresh mid-run (in-flight query completes on old CRC, next query sees new data).
  2. Concurrency: parallel golden queries on the same segments — per-query buffers independent, in-query dedup works, no cross-query interference.
  3. Chaos: MinIO killed mid-query → flagged partial + circuit breaker + self-heal on restart; slow S3 (latency injection) → deadline semantics hold, no thread leaks.
  4. Memory: allocation tracking proves buffers freed after every query, including error paths; sustained load shows flat heap/direct-memory.
  5. Bench report: latency by query shape (point filter / aggregate / group-by), GETs/query, bytes/query, $/query, and the classic-path A/B vs master.

10.Deferred by design (future work)

  • Block cache (disk or memory) with budget + LRU + admission — turns repeat queries warm; slots behind the same SegmentDirectory/fetch seams with no redesign.
  • Pinned hot structures (dictionaries, blooms) — the first thing such a cache would hold.
  • Hybrid local/remote per table age (tierConfigs-driven demotion).
  • Prefetch pipelining across operator stages.
