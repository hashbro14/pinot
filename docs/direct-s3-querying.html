Pinot Direct S3 Querying

Serving OFFLINE tables by reading segment bytes straight from the deep store — what was built, how it differs from stock Pinot, and exactly what happens when a query runs.
Fork hashbro14/pinot · branch feature/remote-segment-reads · every number in this document was measured on a real 5,153,926-row table.
Scope of this document: all timings and traces below are from the no-local-cache configuration (remote.cache.enabled=false) — every query reads from the object store, nothing is reused between queries. This is the configuration for judging deep-store cost honestly. The disk-cache mode exists and is described in §9, but it is not what the numbers here reflect.

1.What this changes, in one page

Stock Pinot requires every segment a server is assigned to be downloaded and stored locally before it can be queried. Local disk therefore has to be as large as the data, forever, even for data that is almost never read.

This fork lets an OFFLINE table be marked remote. For such a table the server stores only each segment's metadata (about 36 KB per segment) and reads the actual index bytes from the deep store per query, by byte range, using the segment's index_map to know exactly which bytes to ask for.

Measured on the real table (artist_dashboard_daily_streams_aggregated, 2 segments, 5,153,926 rows): 
Deep store (MinIO)        2.0 GB    both segments' columns.psf — the only full copy
Server segment directory   76 KB    metadata.properties + index_map + creation.meta
columns.psf on the server      0    never downloaded

SELECT COUNT(*)                                 →  6–8 ms      (metadata only, no S3 read)
SELECT COUNT(*) WHERE artist_id = 72            →  75–104 ms   (19,225 matching rows)
SELECT country_code, SUM(all_streams) GROUP BY  →  123–143 ms  (scans all 5.15M rows)
SELECT * WHERE artist_id = 72 LIMIT 100         →  1.8–2.9 s   (all 19 columns needed)

Three properties were treated as non-negotiable and hold today:

  1. Zero effect on normal tables. A table without the remote config runs the byte-identical stock code path — the remote loader delegates to the default loader.
  2. Opt-in twice. An instance-level loader setting and a per-table config.
  3. Degradation is never silent. Failures surface as query exceptions or Pinot's existing flagged partial results.

5.A query, end to end, with real output

The query, run against the live cluster with the disk cache disabled:

SELECT * FROM artist_dashboard_daily_streams_aggregated WHERE artist_id = 72 LIMIT 100

Step 0 — state before the query

MinIO:                    2.0 GB   (2 × columns.psf ≈ 1 GB each)
Server segment directory:  76 KB   metadata only
Server cache directory:    empty   (caching disabled)

Step 1 — broker

Unchanged from stock Pinot. Routing comes from Helix; the broker does not know the table is remote.

Step 2 — segment pruning, no S3 traffic

Each segment's metadata.properties is already in server memory and carries per-column min/max values, so segments that cannot contain artist_id = 72 are eliminated before any byte is read. In this table that removed one of the two segments at zero cost.

Step 3 — fetch planning

SELECT * expands to all 19 columns. The in-memory index_map turns that into exact byte ranges inside columns.psf. Admission control compares the total against the per-query budget (1 GB); over budget, the query is served by ranged reads rather than materialization, so it can never exhaust server memory.

Step 4 — reading, by index type

#What is readWhySize
1artist_id.dictionarybinary search maps the literal 72 → dictionary id~2 MB
2artist_id.inverted_indexdictionary id → bitmap of matching docIds (19,225 of them; LIMIT 100 takes the first 100)16.4 MB
319 × <column>.forward_indexdocId → dictionary id, for each selected column1–7 MB each
419 × <column>.dictionarydictionary id → the actual value to returnup to 390 MB (song_name_arabic)

Step 5 — measured result

rows returned         100
numDocsScanned        100          ← the index worked: 100 of 5,153,926 rows examined
numSegmentsMatched    1            ← pruning worked: 1 of 2 segments

Reading the result. Identification is surgical — 100 documents out of 5.15 million, one segment of two. Fetching is not: roughly 580 MB of dictionaries and forward indexes crossed the wire to produce 100 rows, because the unit of I/O is the index entry, not the row. Closing that gap is the main open item (§10).

6.What happens when the column has no index

This table has an inverted index on artist_id, country_code and owner_id, and bloom filters on artist_id and song_id. Nothing on album_id or song_name. The difference is visible in Pinot's own counters:

QueryFilter pathentriesScannedInFilterdocsScannedTimeS3 GETs
WHERE artist_id = 72 inverted index 019,22575–104 ms28
WHERE album_id = 1009478870 full column scan 5,153,926481–118 ms22
WHERE song_name = 'Amarain' full column scan 5,153,926162202 ms—

What actually differs

  • With an index: read the dictionary (find the value's id), read that id's bitmap from the inverted index, and you have the exact docIds. entriesScannedInFilter = 0 — no rows were examined to evaluate the predicate.
  • Without an index: Pinot must read the column's entire forward index and compare every value. entriesScannedInFilter = 5,153,926 — every row. Remotely, that means the whole forward index must cross the network, not just the part covering matching rows.
Why the wall-clock times look similar here — and why that is misleading. The scan of album_id is only 81–118 ms because its forward index is a dense, dictionary-encoded integer column of about 6 MB: cheap to transfer and fast to scan. The gap widens sharply with column width and cardinality — the same scan over song_name_arabic would mean pulling a 390 MB dictionary plus the forward index. Also note both queries issue a similar number of GETs (28 vs 22): request count follows the number of index entries touched, while bytes follow whether a scan was needed. On real S3, where each request costs 10–30 ms of latency, the unindexed path degrades much faster than these local-MinIO numbers suggest.
Practical rule for remote tables: an index that only saved CPU on a local table now also saves network transfer. Columns used in filters should be indexed far more aggressively than for local tables; scanning is no longer merely slower, it is billable.

7.Measured performance

Table: artist_dashboard_daily_streams_aggregated, 2 daily partitions from s3://anghami-processed-data/dwh/, 5,153,926 rows, 19 columns, 2.0 GB of segment data in MinIO. Server: 4 GB heap, no local cache. Three consecutive runs of each query.

QueryRun 1Run 2Run 3Rows scanned
SELECT COUNT(*)289 ms6 ms8 ms5,153,926 (metadata)
COUNT(*) WHERE artist_id = 72340 ms109 ms94 ms19,225
SELECT * WHERE artist_id = 72 LIMIT 1002,930 ms2,201 ms1,804 ms100
GROUP BY country_code274 ms123 ms143 ms5,153,926
GROUP BY artist_name1,271 ms601 ms767 ms5,153,926
SELECT * LIMIT 101,250 ms1,086 ms1,683 ms10

Zero exceptions in every run. Two observations matter more than the absolute numbers:

  • The times do not converge toward zero. With caching enabled the second run of SELECT * was 52 ms; here it stays around 2 s. Repeatedly slow is the signature of genuinely re-reading the object store each time.
  • Cost tracks columns touched, not rows. A group-by over all 5.15 M rows on one narrow column (country_code) costs ~130 ms; a 100-row SELECT * costs ~2 s, because it must pull 19 dictionaries.
Caveat on absolute numbers: MinIO here runs on localhost — no network latency, no per-request charge. Real S3 adds roughly 10–30 ms of first-byte latency per GET. Query shapes that issue many small reads (SELECT *, unindexed scans) will degrade considerably more than shapes that issue a few large reads. Treat these figures as a lower bound.

8.Fetching only the rows a query needs

The numbers above have an ugly spot in them: a hundred-row SELECT * costs about two seconds, and a thousand-row one cost 4.4 s while moving 789 MB and issuing 1,977 requests — to return roughly a megabyte of data. That is not the filter's fault. On the run below the filter itself accounted for about a millisecond; everything else was fetching.

Why a thousand rows cost a gigabyte

Resolving one dictionary-encoded value is three dependent reads. The forward index gives a dictId; the dictionary's offset table says where that value starts, the next slot says where it ends, and only then can the value bytes be read. Locally each of those is a page-cache hit costing about 100 ns, so nobody has ever had a reason to care. Against object storage each is a round trip. A thousand rows across nineteen columns is on the order of 57,000 of them.

The buffer could not see any of this coming — it was handed one read at a time. Its only defences were guessing ahead (read-ahead, which fetches bytes nobody wants) and giving up and pulling the whole index entry (which fetches tens of megabytes to answer for ten rows). Both were tried, and both lost:

StrategyGETsBytesTime
256 KB fixed read-ahead1,977789 MB4,397 ms
Adaptive 16 KB read-ahead for random access1,953338 MB6,396 ms
Materialize the entry after 96 random reads3331,002 MB6,882 ms

Every one of those is a guess made with one read of context. The information needed to do better already exists one layer up and was being discarded: a projection does not resolve values one at a time, it resolves a block of up to 1,024 docIds at once, and hands the dictionary an entire array of dictIds.

The hint

So the batch is passed down instead of being thrown away. PinotDataBuffer gains two advisory methods — wantsPrefetch() and prefetchRanges(offsets, lengths, count) — that local buffers ignore entirely, because for them a read is a memory access and describing it in advance is pure overhead. The remote buffer implements them: it sorts the ranges, merges any pair close enough that reading the hole between them is cheaper than a second request, and fetches the result in a handful of ranged GETs. Every subsequent read is then served from what was already pulled.

Three call sites feed it, each being a place where a whole batch is already in hand:

  • Forward indexes (FixedBitIntReader, FixedBitIntReaderWriter): values are bit-packed at a fixed width, so a docId maps to a byte range arithmetically — nothing has to be read to plan the fetch.
  • Fixed-width dictionaries (FixedByteValueReaderWriter): same, at dictId × width.
  • Variable-length dictionaries (VarLengthValueReader): two phases, because a value's extent is itself stored in the dictionary. First fetch the batch's offset slots — they live in one contiguous table, so a thousand scattered dictIds coalesce into very little — then read them, now local, to learn where the values are, and fetch those.

The hooks sit on the batch read*Values methods of BaseImmutableDictionary, so every column type inherits the behaviour, not just strings.

Turning off the eager fetch

One thing had to be removed for the hint to matter. Acquiring a segment used to pull every index entry the query planner listed, whole, up to the promote ceiling. For a full scan that is exactly right. For a ten-row lookup it is the entire problem: nineteen columns pulled whole is ~300 MB regardless of how few rows come back. Eager prefetching is now off by default (remote.eager.prefetch.enabled restores it). Nothing is lost for scans — a query that really does read an entry end to end still gets it in a single read via the existing promote-on-miss path, and prefetching declines any batch spanning more than a quarter of an entry precisely so that path stays in charge.

Result

Same query, same data, same server — SELECT * FROM artist_dashboard_daily_streams_aggregated WHERE all_video_streams = 0 LIMIT 1000, measured from MinIO's own request counters:

BeforeAfter
Time4,397 ms~480 ms7.9× faster
Bytes read789 MB89 MB8.9× less
GET requests1,9772579× fewer

The request count is the number that matters most for real S3. At 10–30 ms of first-byte latency, 1,977 requests is 20–60 s of latency alone even if the bytes were free; 25 requests is under a second. Meanwhile the shapes that were already good did not regress — a full-scan GROUP BY artist_id over all 2.59 M rows still reads 11 MB in 4 requests and ~260 ms, because prefetching correctly declines to get involved.

The remaining 89 MB is a deliberate trade, not a leftover. A thousand rows scattered across 2.59 M leave small holes between the ranges they need. Merging across those holes reads bytes nobody asked for; splitting on them costs a round trip each. The merge distance is remote.prefetch.coalesce.gap.bytes (32 KB by default), tuned for object storage, where a request costs tens of milliseconds and bandwidth is cheap. Lower it when the deep store is nearer or the rows are sparser.

9.How to prove it is really reading S3

a. Watch the requests

docker run --rm --network docker_pinotnet --entrypoint sh \
  quay.io/minio/mc:RELEASE.2025-04-16T18-13-26Z \
  -c 'mc alias set l http://minio:9000 pinotaccess pinotsecret >/dev/null; mc admin trace --verbose l' > trace.log
# run the query, then
grep -c GetObject trace.log                       # → 274
grep -oE "Range: bytes=[0-9]+-[0-9]+" trace.log   # → Range: bytes=17419741-17613962 …

b. Stop the deep store — the query must fail

docker stop pinot-minio && <run query>

rows returned: 0
exception:     Failed ranged read of artist_id.bloom_filter [0, +194222)
               for segment: artist_dashboard_daily_streams_aggregated_OFFLINE_2026-08-04…

This is the decisive test: if any of the data were resident locally, the query would have succeeded. It failed on the very first read. After restarting MinIO the query recovers on its own — though the first attempt after recovery fails on stale pooled connections, then succeeds (1,867 ms, 1,736 ms).

c. Inspect the disk

docker exec pinot-server du -sh /tmp/pinot/server/data /tmp/pinot/remote-cache
  76K   /tmp/pinot/server/data      ← metadata only
  (none) /tmp/pinot/remote-cache    ← caching disabled

docker exec pinot-server sh -c 'ls /tmp/pinot/server/data/*/*/v3/columns.psf | wc -l'
  0

d. Watch memory settle

docker exec pinot-server jcmd 1 GC.run; docker exec pinot-server jcmd 1 GC.heap_info
  garbage-first heap  total 2840576K, used 839880K

Heap returns to a baseline between queries rather than growing — entries are released when the query ends.

10.Configuration reference

Table (OFFLINE only)

"metadata": {
  "customConfigs": {
    "remote.query.enabled":  "true",
    "remote.query.base.uri": "s3://my-bucket/pinot-deepstore/myTable/"
  }
}
The key is metadata, not customConfigs, at the top level of the table config — Pinot's JSON name for TableCustomConfig is metadata. Getting this wrong is silent: the table is created successfully and simply behaves as a normal table.

Deep-store layout

Segments must be published untarred, because a .tar.gz cannot be range-read: 

s3://bucket/pinot-deepstore/myTable/<segmentName>/v3/
    columns.psf            ← read by ranged GET at query time
    metadata.properties    ← fetched once at segment load
    index_map              ← fetched once at segment load
    creation.meta          ← fetched once at segment load

Server

# server config file
pinot.server.instance.segment.directory.loader=remote   # non-remote tables delegate to the default loader
pinot.server.query.executor.enable.prefetch=true        # upstream flag; drives the fetch planner

# JVM system properties
-Dpinot.server.instance.remote.cache.enabled=false          # ← the mode used in this document
-Dpinot.server.instance.remote.query.max.fetch.bytes=1G     # per-query admission budget
-Dpinot.server.instance.remote.promote.max.bytes=128M       # larger entries are read in ranges
-Dpinot.server.instance.remote.fetch.parallelism=8
-Dpinot.server.instance.remote.fetch.timeout.seconds=30
-Dpinot.server.instance.remote.coalesce.gap.bytes=256K

# --- batched reads (see §8) ---------------------------------------------
-Dpinot.server.instance.remote.eager.prefetch.enabled=false      # ← default; true restores whole-entry
                                                                 #   fetching at acquire time
-Dpinot.server.instance.remote.prefetch.coalesce.gap.bytes=32K   # merge distance within one batch:
                                                                 #   the bytes-vs-round-trips dial
-Dpinot.server.instance.remote.prefetch.max.bytes=32M            # past this, read the entry whole

The optional disk cache (not used above)

Setting remote.cache.enabled=true streams each fetched entry to a local file and mmaps it, bounded by remote.cache.max.bytes with LRU eviction. It changes the performance profile completely — the same SELECT * measured 1,359 ms cold and 52 ms warm — at the cost of local disk. It is described here only for completeness; every number elsewhere in this document is from the cache-disabled configuration.

11.Limits, known gaps, and what comes next

Design limits inherent to the approach

  • The deep store is a hard dependency. If it is unavailable, remote tables cannot serve queries at all.
  • Cold latency is the trade. Every query pays deep-store cost in this mode; there is no configuration that makes a remote read as fast as a local one.
  • OFFLINE tables only. REALTIME, upsert, and dedup tables need local segments.

Implementation gaps (tracked, not yet fixed)

  • Fetch granularity is the entry, not the document. A 100-row result pulled ~580 MB. An implementation that fetched only the pages holding those docIds would need on the order of 1 MB — roughly two orders of magnitude better. The blocker is not the reader, which already supports ranged reads, but the planner: it must pass query selectivity so prefetch can choose "coalesced ranges" for a selective filter and "bulk fetch" for a scan. Measured evidence for why this must be selectivity-driven rather than size-driven: with a 32 MB promote ceiling the selective query improved from 622 MB / 7.1 s to 217 MB / 2.4 s, while a cold group-by regressed from ~1.1 s to a timeout.
  • Ranged reads bypass the disk cache when it is enabled — the largest entries, which are the most expensive to fetch, are the ones never cached.
  • No metrics. The counters exist in code (fetch count and bytes, cache hits/misses, sync-misses, degraded fetches) but are not exposed through ServerMetrics, so today's verification is manual (§8).
  • Cache invalidation is not wired to segment delete or refresh; CRC keying keeps this correct but leaks space until eviction.
  • Star-tree and text indexes are not served remotely; entries above 2 GB are rejected.
  • Reload/refresh of a remote segment is unsupported — the directory is read-only.

Operational notes learned while building this

  • The container's IP is part of a Pinot server's Helix identity; recreating a container gives it a new identity and orphans its segment assignments. The compose file pins a static IP for this reason.
  • docker compose down destroys MinIO data unless a named volume is declared.
  • Deleting the cache directory under a running server used to break every subsequent query; the cache now recreates its directory on demand.

12.Running it yourself

# 1. build the launcher jar from the fork
cd ~/Desktop/pinot-s3/pinot
JAVA_HOME=<jdk21+> ./mvnw -q -pl pinot-tools -am -DskipTests install

# 2. build the image (the jar plus a launcher script with the required --add-opens flags)
cp pinot-tools/target/pinot-tool-launcher-jar-with-dependencies.jar /tmp/pinot-img/pinot-all.jar
cd /tmp/pinot-img && docker build -t pinot-s3-query:local .

# 3. start MinIO + ZooKeeper + controller + broker + server
cd ~/Desktop/pinot-s3/docker && docker compose up -d

# 4. create the table and publish segments untarred to MinIO, then register them
curl -X POST -H 'Content-Type: application/json' --data-binary @adsa-schema.json http://localhost:9000/schemas
curl -X POST -H 'Content-Type: application/json' --data-binary @adsa-table.json  http://localhost:9000/tables
#   (upload each segment's v3/ directory to s3://pinot-deepstore/<table>/<segment>/v3/,
#    then POST the segment tar to /v2/segments so Helix assigns it)

# 5. run the benchmark used for §7
./poc-s3-only.sh 3

Useful endpoints: broker localhost:8099, controller localhost:9000, MinIO console localhost:9101 (pinotaccess / pinotsecret).
